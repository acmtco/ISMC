**Задача №7.** Автоматизированный сервис поиска нарушений на строительных

## Выбранный подход и ключевые технологии

Система переводит снимки с камер в **машино-часы** — ту же единицу, в
которой составлен календарный график и смета. Это даёт общий язык между
видеопотоком и графиком: сравниваются не «есть техника / нет техники», а
план и факт в одних единицах, с накопительным итогом и прогнозом.

Поверх машино-часов работают пять правил отклонений (Р0–Р4), каждое со
своей формулировкой для прораба, числами плана и факта и кадрами-уликами.

| Слой | Технология | Почему так |
|---|---|---|
| Детекция | YOLO11 (ultralytics), дообучение | Один из лучших компромиссов «скорость/качество» на CPU; ТЗ прямо допускает дообучение готовых моделей |
| Трекинг | BoT-SORT + собственная склейка разрывов | Снимки приходят раз в 10–20 минут, штатная ассоциация соседних кадров не работает — склеиваем треки по времени и расстоянию |
| Состояние техники | Оптический поток Фарнебака + HSV-дисперсия + MAD бокса → логистическая регрессия | Различает «работает» и «простаивает»; опубликованный ориентир Edge-IMI на одних bbox-признаках даёт F1 = 0.76, добавление потока должно дать больше |
| Аналитика | pandas / numpy, правила в YAML | Ни одного порога в коде — все в `config/`, методику можно править без программиста |
| API | FastAPI + Pydantic v2 | OpenAPI-схема на русском как часть демонстрации |
| Хранилище | SQLite (dev) / PostgreSQL (prod) | Смена — одна переменная окружения |
| Интерфейс | React 18 + Vite + TypeScript | Пять экранов, тёмная «промышленная» тема |
| Запуск | Docker Compose | Одна команда |

## Процесс обнаружения техники

Кадр проходит пять шагов, результат каждого фиксирован контрактом
`docs/02-data-contract.md`:

1. **Оценка качества.** Дисперсия лапласиана (размытие), средняя яркость
   (ночь), доля однородных ячеек сетки 8×8 (залепленный объектив). Сводный
   `score < 0.5` — кадр исключается из расчёта, но попадает в `coverage`
   суток. Это ключевое место: на плохих данных система **не формирует
   отклонений вообще**, потому что ложная тревога дороже пропущенной.
2. **Детекция.** YOLO11, 12 классов техники. Восемь из ТЗ покрыты
   полностью, четыре добавлены под справочник работ ДГП.
3. **Трекинг.** BoT-SORT ассоциирует объекты между кадрами, собственный
   `TrackStitcher` склеивает разрывы `track_id` по времени (до 60 с) и
   расстоянию между центроидами (до 80 px) внутри одного класса и зоны.
4. **Привязка к зоне.** Объект относится к полигону по **точке опоры** —
   центру нижней грани бокса. Принципиально: стрела крана висит над одной
   зоной, а стоит он в другой.
5. **Классификация состояния** — `active` / `idle` / `parked` / `unknown`.
   Поверх модели жёсткое правило: нет движения дольше двух часов → `parked`,
   и такая техника не учитывается в машино-часах вовсе.

## Схема сопоставления с этапами строительства

```
Снимки ──► детекции ──► треки ──► состояние
                                      │
                    (сутки × зона × класс техники)
                                      ▼
                             МАШИНО-ЧАСЫ ФАКТ
                                      │
   ГПР (XLSX/MS Project) ──► planned_mh ──► сравнение ──► отклонение Р0–Р4
                                      │                          │
                          ресурсный отпечаток              SPI, прогноз,
                          «этап → техника»                 рубли простоя
```

**Ресурсный отпечаток** — методика «этап работ → необходимая техника» из
ТЗ. Для каждого вида работ задано: обязательная техника с минимумом и
типовым количеством, вспомогательная, запрещённая и ритм работы. Пример для
разработки котлована: обязателен экскаватор (минимум 1, типично 2),
вспомогательные — самосвал (2/5) и бульдозер (0/1), запрещены башенный кран
и бетононасос, ритм — 6–12 рейсов самосвала за смену.

Похожесть наблюдаемого состава на ожидаемый:

```
cover       = Σ min(наблюдалось, типично) / Σ типично
excess      = Σ запрещённой техники / Σ всей техники
match_score = 0.55·cover + 0.25·ритм + 0.20·(1 − excess)
```

**Плановые машино-часы** берутся из графика напрямую, если он их содержит, а
иначе выводятся из объёма работ и норм выработки:
`planned_mh = объём / норма_на_машино-час`.

**Правила отклонений:**

| Код | Смысл | Условие срабатывания |
|---|---|---|
| Р0 | Низкое доверие | `coverage < 0.6` или качество < 0.5 — отклонения не формируются |
| Р1 | Ресурсный дефицит | факт < 70 % плана, 2+ суток подряд |
| Р2 | Простой | КИТ ≤ 0.5 при присутствии ≥ 4 ч за смену |
| Р3 | Несоответствие фронта | `match_score < 0.35` или конкурирующий вид работ > 0.6 |
| Р4 | Тишина | техники нет 2+ суток при покрытии ≥ 0.8 |

Приоритет при конфликте: Р0 > Р4 > Р1 > Р3 > Р2 — один явный диагноз на
сутки честнее нескольких противоречащих.

## Текущий прогресс

Готово и проверено: 205 автотестов проходят, `ruff` без замечаний,
фронтенд собирается, API поднимается.

- **Аналитическое ядро** — машино-часы, ресурсный отпечаток, все пять
  правил, SPI, прогноз срыва срока, обратная задача («чтобы уложиться в
  срок, добавьте N единиц техники»), расчёт КИТ и потерь в рублях.
- **Импорт графика** — XLSX и MS Project XML с нечётким сопоставлением
  колонок по словарю синонимов.
- **API** — 12 эндпоинтов, документация на русском, «машина времени» через
  Server-Sent Events, выгрузка PDF-актов по отклонению.
- **Интерфейс** — пять экранов: мастер настройки, площадка сейчас, график
  план/факт, лента отклонений, экономика.
- **Синтетический бенчмарк** — 30 суток с внедрёнными отклонениями и
  честным ground truth; на нём Р3 и Р4 выявляются с точностью и полнотой
  1.00.
- **Детектор** — дообучается на открытом размеченном наборе; пайплайн
  обучения воспроизводим одной командой.

Честное ограничение на сегодня: детектор обучен пока не на всех классах, и
до завершения разметки метрики распознавания в отчёт не выносятся. Все
числа в проекте берутся только из прогона `scripts/eval_end2end.py` —
цифр «из головы» в документах нет.

## План до финальной сдачи

1. Разметить 100 снимков ДГП под 12 классов; пополнить выборку открытыми
   датасетами из списка организаторов.
2. Дообучить YOLO11 на полном перечне, замерить mAP по классам ТЗ отдельно.
3. Собрать собственный проверочный набор с разной освещённостью, сезонностью
   и ракурсами — как требует ТЗ.
4. Переложить ресурсные отпечатки на официальный справочник видов работ ДГП
   (380 позиций) вместо текущих семи обобщённых типов.
5. Заполнить раздел устойчивости в метриках: ночь, дождь, перекрытие,
   припаркованная техника.
6. Развернуть прототип по адресу, доступному жюри.
7. Сверить нормы выработки с ЕНиР/ГЭСН и подтвердить ставки машино-часа
   проверяемым источником.
