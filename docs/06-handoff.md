## 1. Что это за проект

Система «Хронограф» для конкурса «Лидеры цифровой трансформации 2026»,
задача №7. Постановщик — Департамент градостроительной политики Москвы,
эксперты — ГАУ «Институт Генплана Москвы».

**Одна фраза, ради которой всё делается** (из `CLAUDE.md`):

> Мы не «детектируем технику на камере». Мы превращаем видеопоток в
> **машино-часы** — нативную единицу календарного графика и сметы — и
> автоматически сверяем фактические машино-часы с плановыми, выдавая
> типизированные отклонения с доказательствами и прогнозом срыва срока.

Продуктовая логика в одну строку:

```
кадр → детекция → трек → состояние (работает/простой/на приколе)
     → машино-часы по (сутки × зона × класс)
     → сверка с ГПР → отклонение Р0–Р4 → прогноз срыва + рубли
```

### Терминология (язык заказчика, использовать строго так)

| Термин | Значение |
|---|---|
| **МЧ** | машино-час; `mh_present` — часы присутствия, `mh_active` — часы работы, `mh_idle = present − active` |
| **КИТ** | коэффициент использования техники = `mh_active / mh_present` |
| **SPI** | индекс выполнения по срокам = факт МЧ / план МЧ на дату |
| **Зона выполнения** | размеченный полигон на кадре, к которому привязана работа |
| **Ресурсный отпечаток** | ожидаемый состав и интенсивность техники для вида работ |
| **ГПР** | график производства работ (календарный график) |
| **Отклонение** | типизированное расхождение факта с графиком (Р0–Р4) |

### Чего проект сознательно НЕ делает

- Не распознаёт людей и не считает нарушения ТБ (другая задача конкурса).
- Не строит 3D-реконструкцию и не сравнивает с BIM.
- Не читает госномера техники.
- Не претендует на юридически значимый учёт — даёт основание для проверки.

Практическое следствие правила 4, которое видно по всему коду: везде, где
данных нет (нет весов детектора, нет расписания, нет детекций), система

## 5. Механика камер — подробно

### 5.1 Паспорт камеры

Камеры не создаются через API — они описаны в `data/ref/objects.json`
(контракт `docs/02`, раздел 1) и засеиваются в БД при старте:

```json
{
  "camera_id": "CAM-01",
  "title": "Северный ракурс",
  "source": {"kind": "replay", "uri": "data/synthetic/CAM-01/"},
  "capture_interval_sec": 1200,
  "zones": [
    {"zone_id": "Z-PIT", "title": "Котлован",
     "polygon": [[60,300],[560,295],[600,480],[40,490]], "area_m2": 2400}
  ],
  "homography": null
}
```

`capture_interval_sec: 1200` — 20 минут. Это не «видео», а **редкие снимки**:
именно так работают реальные строительные камеры, и вся арифметика МЧ
построена на этом (см. §5.5).

### 5.2 Четыре типа источника

`services/perception/source.py`, фабрика `open_source()` по `source.kind`:

| `kind` | Класс | Как работает |
|---|---|---|
| `rtsp` | `RtspSource` | `cv2.VideoCapture(uri)`, кадры с `datetime.now()`; при неудаче — `ConnectionError` с понятным текстом |
| `hls` | `HlsSource` | наследник `RtspSource`, поведение идентично; отдельный класс — для ясности контракта |
| `folder` | `FolderSource` | файлы `<YYYYMMDDTHHMMSS>.jpg` из папки, метка времени парсится **из имени файла**, таймзона Europe/Moscow |
| `replay` | `ReplaySource` | тот же `FolderSource` + опциональная пауза между кадрами = `(реальный интервал)/speed` |

Общий интерфейс — `iter_frames() → Iterator[Frame]`, где
`Frame(ts, image, uri)`, изображение BGR как в OpenCV.

`ReplaySource(speed=None)` отдаёт кадры без задержек (пакетная обработка,
оценка); `speed=60` — прокрутка в 60× быстрее реального времени для демо.

### 5.3 Опрос камер планировщиком

`services/api/scheduler.py`, задача `poll_cameras_job`, интервал
`config/api.yaml: scheduler.poll_interval_sec` (сейчас 300 с).

Логика, шаг за шагом:

1. **Если `HG_MODE != "live"` — опрос не выполняется вовсе.** Для
   replay-камер данные предрассчитаны, крутить нечего (правило 3).
2. Опрашиваются только камеры с `source_kind ∈ {rtsp, hls, folder}`.
3. При первом опросе камеры лениво собирается `IncrementalPipeline`:
   - `Detector` — веса форсированно загружаются сразу, чтобы поймать их
     отсутствие **здесь**, а не в середине обработки. Нет весов →
     `logger.warning` и `return 0`, камера просто пропускается;
   - `StateClassifier.load(models/state.joblib)` — нет модели → тот же
     честный пропуск;
   - состояние пайплайна кэшируется в модуле (`_pipeline_state`) и живёт,
     **пока жив процесс API**. Перезапуск процесса начинает треки заново.
4. Кадры читаются из источника; уже обработанные отсекаются по
   `_last_polled_ts[camera_id]` (сравнение ISO-строк).
5. Каждый кадр → `pipeline.process_frame(frame)` → строка дописывается
   (`append`) в `data/interim/detections/<camera_id>.jsonl`.
6. Исключение на одной камере ловится и логируется — **один сбой камеры не
   роняет опрос остальных**.

### 5.4 Что происходит с кадром внутри перцепции

`services/perception/pipeline.py` связывает пять модулей:

**(1) `quality.py` — оценка качества кадра.** Считает: `blur` (дисперсия
лапласиана, эталон резкости `SHARP_VARIANCE_REF = 400.0`), `night`
(средняя яркость < 70), `occlusion` (доля ячеек сетки 8×8 с локальной
дисперсией < 25 — залепленный объектив/перекрытие), и сводный `score`.
**Порог `score < 0.5`** — кадр исключается из расчёта МЧ, но учитывается в
`coverage` суток.

**(2) `detect.py` — YOLO-обёртка.** Конфиг из `config/perception.yaml`:
`imgsz 640`, `conf_threshold 0.35`, `iou_threshold 0.5`, `device cpu`.
Классы: `excavator`, `dump_truck`, `concrete_mixer`, `concrete_pump`,
`tower_crane`, `mobile_crane`, `bulldozer`, `roller`, `loader`,
`drilling_rig`, `worker`.

**(3) `track.py` — BoT-SORT + `TrackStitcher`.** Зачем своя склейка:
BoT-SORT ассоциирует объекты между **соседними кадрами плотного видео**, а
у нас кадры раз в 20 минут. `TrackStitcher` склеивает `track_id` по времени:
разрыв до `max_gap_seconds` (60 с по умолчанию, для 20-минутной синтетики
eval поднимает до `capture_interval × 1.5`) при расстоянии между
центроидами до `max_centroid_distance_px = 80`, только внутри одного класса
и одной зоны.

**(4) `zones.py` — привязка к зоне.** Объект относится к зоне по
**точке опоры** — центру нижней грани бокса (точка касания земли), а не по
центру бокса. Это принципиально: стрела крана «висит» над одной зоной,
стоит в другой.

**(5) `state.py` — классификатор состояния.** Четыре признака в скользящем
окне `feature_window_sec` (90 с):

| Признак | Что это |
|---|---|
| `centroid_mad` | MAD смещения центра нижней грани бокса |
| `area_mad` | MAD площади бокса |
| `flow_mag` | средняя величина оптического потока Фарнебака внутри бокса |
| `hsv_var` | дисперсия HSV **по каналам** внутри бокса (текстура: работающий двигатель даёт более «шумную» картинку) |

Модель: `Pipeline(StandardScaler, LogisticRegression)` → `models/state.joblib`.
Поверх модели — **жёсткое правило**: без движения дольше
`parked_after_hours = 2.0` → `parked`, независимо от предсказания.
Предсказуемость важнее точности модели в этом крайнем случае.

Ориентир из литературы — Edge-IMI (YOLOv8 + ByteTrack + логрегрессия только
на bbox-признаках): accuracy 0.79, F1(active) 0.76. Наш прирост должен
объясняться добавлением оптического потока и цветовой дисперсии.

Результат — одна строка `detections.jsonl` на кадр (`docs/02`, §3):

```json
{"camera_id":"CAM-01","ts":"2026-09-20T08:30:00+03:00",
 "frame_uri":"data/replay/CAM-01/20260920T083000.jpg",
 "quality":{"blur":0.12,"night":false,"occlusion":0.03,"score":0.94},
 "objects":[{"track_id":17,"cls":"excavator","conf":0.91,
   "bbox":[412,388,180,120],"zone_id":"Z-PIT","state":"active","state_conf":0.83,
   "features":{"centroid_mad":4.7,"area_mad":311.0,"flow_mag":1.94,"hsv_var":480.0}}]}
```

### 5.5 Как редкие кадры превращаются в часы

`services/analytics/machine_hours.py` — **сердце продукта**.

Каждый кадр «отвечает» за интервал до следующего кадра, но не больше
`max_gap_sec` (3600 с). Последнему кадру суток приписывается номинальный
интервал съёмки. Ограничение обязательно — иначе один редкий ночной кадр
приписал бы себе всю ночь.

Три правила исключения (все — из правила 4):

- `state == "parked"` **не учитывается в МЧ вообще** — ни в `present`, ни в
  `active`. Техника «на приколе» не в работе.
- `state == "unknown"` тоже не учитывается — не смогли классифицировать,
  честнее не засчитывать, чем гадать.
- `quality.score < 0.5` — кадр не участвует в расчёте, но **учитывается в
  `coverage`** суток.

Агрегат — одна строка на (дата × зона × класс):

```json
{"date":"2026-09-20","object_id":"OBJ-001","zone_id":"Z-PIT","cls":"excavator",
 "units_seen":2,"mh_present":16.0,"mh_active":11.4,"mh_idle":4.6,
 "utilization":0.71,"coverage":0.93,"confidence":0.88}
```

`coverage` = доля суток, покрытая пригодными кадрами.
`confidence` = `avg_quality_score × coverage`.
**`coverage < 0.6` → отклонения по этой зоне не формируются.**

`daily_quality()` считается по **всем** кадрам камеры, даже если техники в
них нет — иначе нельзя отличить Р4 «тишина» от Р0 «не хватает данных».

### 5.6 Разметка зон из интерфейса

Единственная операция с камерой, доступная через API:

## 6. Механика ГПР — подробно

### 6.1 Импорт графика

`services/analytics/schedule_io.py`, endpoint
`POST /api/objects/{object_id}/schedule` (multipart, `.xlsx` или `.xml`).
Импорт **заменяет** график объекта целиком.

Поддерживаются два формата:
- **XLSX** (`import_xlsx`) — один лист (первый или по имени), первая строка
  заголовки;
- **MS Project XML / MSPDI** (`import_msp_xml`) — включая пользовательские
  поля через `ExtendedAttribute`.

**Нечёткое сопоставление колонок.** Заголовок нормализуется (нижний
регистр, `ё→е`, выброс пунктуации), затем сравнивается со словарём
синонимов `FIELD_SYNONYMS` через `difflib.SequenceMatcher`; порог
`COLUMN_MATCH_THRESHOLD = 0.6`. Распознаются: `name`, `start`, `finish`,
`volume_qty`, `volume_unit`, `zone`, `work_type`, `predecessors`.

Отдельно `match_resource_columns()` ищет колонки-**классы техники** по
русским синонимам (`ru_text.CLASS_RU_SYNONYMS`) — если в графике уже есть
плановые машино-часы по экскаваторам/самосвалам, они берутся напрямую.

Даты принимаются в форматах `%Y-%m-%d`, `%d.%m.%Y`, `%d/%m/%Y`.
Предшественники разбираются как ссылки на номер строки/UID с отбрасыванием
модификаторов лага: `12FS+2d` → предшественник №12.

### 6.2 Определение вида работ

Если колонки `work_type` нет, вид работ выводится из **названия** работы по
ключевым словам (`WORK_TYPE_KEYWORDS`) — эвристика, не ML: прозрачна и
правится руками, когда ошиблась.

```
earthworks_excavation ← котлован, выемк, разработка грунт, земляны
piling                ← сва, буров
foundation_slab       ← фундамент, плита
frame_assembly        ← каркас, монтаж конструкц, монтаж колонн, монтаж плит перекрыт
backfill              ← засыпк
facade                ← фасад
utilities             ← сети, коммуникац, инженерн
```

### 6.3 Вывод `planned_mh` — ключевое поле

`planned_mh` (плановая потребность в машино-часах по классам техники) — то,
с чем сверяется факт. Если его нет в источнике, он выводится из объёма
работ и норм выработки `data/ref/productivity.json`:

```
planned_mh[c] = qty / productivity_per_mh[c]
```

Например, `earthworks_excavation`, 12 000 м³:
экскаватор 66 м³/маш.-ч → 182 маш.-ч; самосвал 28 → 429; бульдозер 200 → 60.

⚠️ Нормы в `productivity.json` помечены как **оценочные, требуют сверки с
ЕНиР/ГЭСН** перед публикацией цифр. Это записано в самом файле (`_source`).

Нормализованный результат — `schedule.json` (`docs/02`, §2):

```json
{"work_id":"W-014","wbs":"2.1.3","name":"Разработка котлована",
 "work_type":"earthworks_excavation","zone_id":"Z-PIT",
 "start_plan":"2026-09-15","finish_plan":"2026-10-02",
 "volume":{"unit":"м3","qty":12000},
 "planned_mh":{"excavator":180.0,"dump_truck":420.0,"bulldozer":60.0},
 "predecessors":["W-011"]}
```

### 6.4 Ресурсный отпечаток и `match_score`

`services/analytics/matching.py` + `data/ref/work_signatures.json`.

Для каждого вида работ описано: `required` (ключевая техника с `min` и
`typical`), `supporting` (вспомогательная), `forbidden` (техника, которой
здесь быть не должно), `rhythm` (метрика интенсивности с `min`/`typical`).

Пример — `earthworks_excavation`: обязателен экскаватор (min 1, typical 2),
вспомогательные — самосвал (2/5) и бульдозер (0/1), запрещены башенный кран
и бетононасос, ритм — 6/12 рейсов самосвала за смену.

```
cover(w)    = Σ_c min(o_c, typical_c) / Σ_c typical_c
excess(w)   = Σ_{c∈forbidden} o_c / (Σ_c o_c + ε)
rhythm(w)   = 1 − |observed_rhythm − typical| / typical, clip[0,1]
match_score = 0.55·cover + 0.25·rhythm + 0.20·(1 − excess)
```

Веса и `ε = 1e-6` — `config/matching.yaml`.
Порог низкой уверенности `low_confidence_threshold = 0.35`.

Честное упрощение, задокументированное в коде: в движке отклонений ритм
считается **нейтральным (1.0)** — подсчёт реальных «рейсов» требует данных
о заходе/выходе из зоны по трекам, которых нет в контракте
`machine_hours.jsonl`.

Отдельный случай — `facade`: ключевая техника (подъёмник) не входит в
перечень распознаваемых классов, поэтому `cover` для него всегда 0 и
**отклонения по фасадным работам не формируются вовсе**. Записано прямо в
`work_signatures.json`.

### 6.5 Правила отклонений Р0–Р4

`services/analytics/deviations.py`, пороги — `config/thresholds.yaml`.

Классификация идёт **по суткам, по приоритету** — честнее один явный
диагноз на день, чем несколько противоречащих:

```
R0 (нет данных) > R4 (тишина) > R1 (дефицит) > R3 (несоответствие) > R2 (простой)
```

Затем однотипные подряд идущие сутки одной зоны схлопываются в «пробег»
(`_consecutive_runs`) → одна карточка отклонения. Если пробег короче
минимума правила — отклонение **не формируется вовсе** (не понижается до
другого правила; осознанное упрощение).

| Правило | Условие | Пороги |
|---|---|---|
| **Р0** `low_confidence` | мало данных / плохое качество | `coverage < 0.6` или `quality < 0.5` |
| **Р1** `resource_gap` | факт МЧ ниже плана | `mh_fact < 0.7 × mh_plan`, ≥ 2 суток подряд, `coverage ≥ 0.6`; severity=high при задержке ≥ 3 сут |
| **Р2** `idle` | техника есть, но не работает | КИТ ≤ 0.5 при `mh_present ≥ 4.0` ч/смена; severity=high при убытке > 50 000 ₽ за период |
| **Р3** `front_mismatch` | в зоне не та техника | `match_score < 0.35`, либо конкурирующий вид работ с `match_score > 0.6`; severity=high от 3 суток |
| **Р4** `silence` | техники нет вообще | ≥ 2 суток подряд при `coverage ≥ 0.8` |

Р0 сознательно **не участвует** в оценке precision/recall — это не
аномалия, которую надо «поймать», а служебная метка.

Карточка отклонения содержит (правило 5): наблюдаемое, ожидаемое, SPI,
`delay_days`, `idle_cost_rub`, объяснение и рекомендацию **на русском**,
кадры-улики, ссылку на строку графика. Русские формулировки —
`services/analytics/ru_text.py`.

По карточке можно сформировать PDF-акт: `POST /api/deviations/{id}/act`.
Кириллица рендерится по-настоящему — шрифты DejaVu лежат в
`data/ref/fonts/` (свободная лицензия, файл `LICENSE_DEJAVU.txt` там же).

### 6.6 Прогноз срыва срока и обратная задача

`services/analytics/forecast.py`:

```
mh_plan_to_date(t)  = planned_mh_total × прошедшие_сутки / всего_суток   (линейно)
mh_fact_to_date(t)  = Σ mh_active накопленным итогом
SPI                 = mh_fact_to_date / mh_plan_to_date
rate(t)             = скользящее среднее mh_active за 7 суток, ч/сут
forecast_finish     = t + ⌈(mh_plan_total − mh_fact_total) / rate⌉
delay_days          = forecast_finish − finish_plan
```

Светофор SPI (`config/thresholds.yaml`): `≥ 0.95` зелёный, `≥ 0.80` жёлтый,
ниже — красный.

**Обратная задача — главная фича для руководителя.** Не «вы отстаёте на N
дней», а «чтобы уложиться в срок, нужно добавить X единиц техники»:

```
required_rate = (planned_mh_total − fact_to_date) / оставшиеся_сутки
gap           = required_rate − текущий_rate
доп. единиц класса c = ⌈gap × доля_класса_c / shift_hours⌉,  shift_hours = 8.0
```

Допущение: одна дополнительная единица даёт полную смену без простоев —
упрощение, **консервативное в пользу подрядчика** (эффект добавленной
техники честно завышен, то есть система скорее недооценит нужное
количество, чем потребует лишнего). Записано в докстринге.

### 6.7 Ночной пересчёт

`scheduler.py: nightly_recompute_job`, по крону в 02:00 Europe/Moscow
(`config/api.yaml`). **Не зависит от режима** `live`/`replay`.

Для каждого объекта: собирает все `detections.jsonl` его камер →
`aggregate_machine_hours` → `daily_quality` → **полностью заменяет** строки
`MachineHourRecord` и `DeviationRecord` этого объекта → прогоняет
`DeviationEngine.run(schedule, machine_hours, daily_quality, as_of)` →
сохраняет отклонения. Сбой на одном объекте не роняет пересчёт остальных.

Если детекций нет — `return 0` без ошибки. Это нормальное состояние на
раннем этапе, а не сбой.

FastAPI, OpenAPI на русском (`/docs` показывается экспертам на питче).
12 эндпоинтов:

```
GET  /health

GET  /api/objects/{id}                         карточка объекта
```

**«Машина времени»** (`routers/replay.py`) — Server-Sent Events. Проигрывает
уже накопленные детекции за период с паузами, пропорциональными реальному
интервалу съёмки, делённому на `speed` (по умолчанию `HG_REPLAY_SPEED=60`).
Пауза ограничена сверху `MAX_EVENT_DELAY_SEC = 5.0` — иначе ночной разрыв
подвесил бы поток на реальные минуты. Это защита UX, а не бизнес-правило,
поэтому константа в коде, а не в конфиге. Питч: «прокручиваю тридцать суток
строительства за десять секунд».

Хранилище — SQLModel/SQLite, `HG_DB_URL` (для PostgreSQL менять только
переменную). `db.py` кэширует движок; `reset_engine_cache()` существует ради
изоляции тестов. При старте (`lifespan`) — `init_db()` + `seed_all()` из
`data/ref/objects.json` и `data/ref/schedule.json` (второго файла сейчас
нет — это не ошибка).

**CORS** добавлен 2026-09-03: `HG_CORS_ORIGINS` (по умолчанию
`http://localhost:${HG_WEB_PORT}`). Без него браузер блокировал запросы с
:5173 на :8000.

## 10. Юнит-экономика

Разделяем две разные вещи: **экономика клиента** (что система экономит
заказчику) и **экономика системы** (сколько стоит её эксплуатация).

### 10.1 Экономика клиента — ценность

Формула, а не круглое число (`docs/04-metrics.md`, §8;
`services/analytics/economics.py`):

```
КИТ                = mh_active / mh_present
mh_idle            = mh_present − mh_active
Потери от простоя  = Σ_техника ( mh_idle × стоимость_машино_часа )
Эффект             = Потери × доля_устранимых_простоев
```

Ставки — `data/ref/machine_hour_cost.json` (₽/маш.-ч, аренда с оператором
и топливом):

| Класс | ₽/маш.-ч | Класс | ₽/маш.-ч |
|---|---|---|---|
| Буровая установка | 5 000 | Бульдозер | 2 800 |
| Бетононасос | 4 500 | Экскаватор | 2 500 |
| Башенный кран | 3 500 | Бетоносмеситель | 2 200 |
| Автокран | 3 000 | Самосвал | 1 800 |
| Погрузчик | 1 700 | Каток | 1 500 |

**Иллюстрация порядка величины** (арифметика от ставок выше, не измерение):
один экскаватор, смена 8 ч, КИТ 0.5 → 4 ч простоя × 2 500 ₽ = **10 000 ₽ в
сутки на единицу**. Парк из десяти машин смешанного состава со средней
ставкой ~2 500 ₽ и КИТ 0.5 — порядка **100 000 ₽/сутки**, около
**3 млн ₽/месяц** на один объект. Это и есть та величина, против которой
меряется стоимость системы (§10.2).

⚠️ **Три обязательные оговорки.**

1. Ставки в `machine_hour_cost.json` помечены в самом файле как **оценка по
   рыночным ставкам, не проверенный источник** — сверить перед питчем.
2. **`доля_устранимых_простоев` сознательно НЕ хранится ни в коде, ни в
   конфиге.** Это допущение, которое обязан обосновать человек, поэтому
   `recoverable_effect_rub()` требует передать его явным аргументом. Не
   вписывайте туда число «чтобы было» — это прямое нарушение правила 4.
3. Наблюдаемый на бенчмарке КИТ в `docs/04-metrics.md` **не заполнен** —
   раздел 8 остался с пустыми ячейками, потому что честного замера не было
   (см. §3, дыра «б»). Пример выше — арифметика от ставок, а не измерение.

Каждое число этой таблицы на питче должно иметь ответ на вопрос «откуда вы
это взяли». Нет ответа — число из презентации убрать.

### 10.2 Экономика системы — себестоимость

`scripts/eval/performance.py`, замер от 2026-08-28
(`docs/04-metrics.md`, §7):

| Метрика | Значение |
|---|---|
| Кадров/сек, CPU (перцепция **без детектора**) | 162.1 |
| Время обработки 1 камеро-суток | 0.2 с |
| Ставка CPU-часа (допущение `CPU_HOUR_COST_RUB`) | 3.0 ₽ |
| Стоимость 1 камеро-суток | ≈ 0.00 ₽ |
| Оценка на 1000 камер/сутки | ≈ 0 ₽ |

Откуда «0.2 с на камеро-сутки»: при интервале 20 мин и окне 07:00–18:00
выходит ~33 дневных + 2 ночных = **35 кадров в сутки на камеру**;
35 / 162.1 ≈ 0.22 с.

⚠️ **Эти нули не значат «система бесплатна».** Из замера исключено самое
дорогое — **инференс YOLO**, потому что весов ещё нет (§3, дыра «а»).
Ставка CPU-часа 3.0 ₽ — тоже допущение в коде, требующее уточнения.

Что можно утверждать честно уже сейчас: **вся не-детекторная часть
конвейера пренебрежимо дешева**, и себестоимость системы будет практически
целиком определяться инференсом детектора. Разумный следующий шаг — после
появления весов замерить кадры/сек с детектором на CPU и на GPU и
пересчитать §7 скриптом (руками в `04-metrics.md` не писать).

Экономическая структура при этом благоприятная: 35 кадров в сутки на
камеру — это **три порядка меньше**, чем у систем, анализирующих видео
25 fps. Редкая съёмка, продиктованная реальными строительными камерами,
оказывается ещё и главным рычагом себестоимости.

**Три грабли, на которые уже наступили** (не повторяйте):

1. Запуск `.venv/bin/uvicorn` как исполняемого файла падает с
   `Operation not permitted` (песочница блокирует shell-скрипт-обёртку).
   Работает только `python3.11 -m uvicorn`.
2. `--app-dir` меняет `sys.path`, но **не меняет cwd процесса**. Все
   относительные пути в `services/api/config.py` (`./data`, `./config`) и
   `DEFAULT_DB_URL = sqlite:///./data/hronograf.db` резолвятся от cwd —
   поэтому переменные окружения обязаны быть абсолютными, иначе
   `sqlite3.OperationalError: unable to open database file`.
3. Без CORS-middleware фронтенд молча уходит в демо-режим. Симптом —
   баннер «Бэкенд недоступен» при живом `/health`.
