# Механизм выявления отклонений

Заказчик просит «понятный механизм выявления отклонений». Понятный —
значит прораб может открыть таблицу, прочитать правило и сказать
«согласен» или «здесь ошибка, поправьте норму». Никакого чёрного ящика.

---

## Шаг 1. Ресурсный отпечаток вида работ

Справочник `data/ref/work_signatures.json`. Для каждого вида работ —
ожидаемый состав техники и характер ритма.

| `work_type` | Наименование | Ключевая техника | Вспомогательная | Характер ритма |
|---|---|---|---|---|
| `earthworks_excavation` | Разработка котлована | экскаватор | самосвал, бульдозер | циклы вывоза, 8–15 рейсов/смена |
| `piling` | Устройство свайного поля | буровая установка | автокран, автобетоносмеситель | длинные стационарные циклы |
| `foundation_slab` | Фундаментная плита | бетононасос | автобетоносмеситель (залп 8–20/сут) | резкий всплеск миксеров |
| `frame_assembly` | Монтаж каркаса | башенный кран | автокран, погрузчик | равномерная крановая активность |
| `backfill` | Обратная засыпка | бульдозер | каток, самосвал | |
| `facade` | Фасадные работы | подъёмник | — | низкий МЧ, высокая доля рабочих |
| `utilities` | Инженерные сети | экскаватор (малый) | автокран | точечные короткие включения |

Формат записи:

```json
{
  "work_type": "earthworks_excavation",
  "required": {"excavator": {"min": 1, "typical": 2}},
  "supporting": {"dump_truck": {"min": 2, "typical": 5},
                 "bulldozer": {"min": 0, "typical": 1}},
  "forbidden": ["tower_crane"],
  "rhythm": {"metric": "dump_truck_cycles_per_shift", "min": 6, "typical": 12}
}
```

`forbidden` — техника, присутствие которой прямо противоречит виду работ.
Это даёт сильный сигнал для отклонения Р3.

## Шаг 2. Оценка похожести (match_score)

Для суток `d` и зоны `z` строим наблюдаемый вектор `o` — машино-часы по
классам техники. Для каждой работы `w`, чей плановый период накрывает `d`
и чья зона совпадает с `z`, считаем:

```
cover(w)    = Σ_c min(o_c, typical_c) / Σ_c typical_c      # насколько закрыт ожидаемый состав
excess(w)   = Σ_{c ∈ forbidden} o_c / (Σ_c o_c + ε)        # доля «запрещённой» техники
rhythm(w)   = 1 - |observed_rhythm - typical| / typical     # совпадение ритма, clip [0,1]

match_score(w) = 0.55·cover + 0.25·rhythm + 0.20·(1 - excess)
```

Веса вынесены в конфиг `config/matching.yaml` — их можно и нужно
калибровать на синтетическом бенчмарке, а не подбирать на глаз.

Победившая работа — с максимальным `match_score`. Если максимум < 0.35,
считаем, что система не может уверенно определить работу → `R0_low_confidence`.

## Шаг 3. Правила отклонений

Все пороги — в `config/thresholds.yaml`. Ни одного магического числа в коде.

### Р1. Ресурсный дефицит — `R1_resource_gap`
```
УСЛОВИЕ: работа w активна по графику
         И mh_fact_день(c) < 0.7 × mh_plan_день(c) для ключевой техники
         И длится ≥ 2 суток подряд
         И coverage ≥ 0.6
SEVERITY: high если delay_days > 3, иначе medium
```

### Р2. Простой — `R2_idle`
```
УСЛОВИЕ: КИТ (mh_active / mh_present) < 0.5 для единицы техники
         И mh_present ≥ 4 ч за смену
         И состояние ≠ parked
ЭФФЕКТ:  idle_cost_rub = mh_idle × стоимость_машино_часа[cls]
SEVERITY: high если idle_cost_rub за неделю > порога
```

### Р3. Несоответствие фронта — `R3_front_mismatch`
```
УСЛОВИЕ: (а) в зоне работает техника из forbidden для плановой работы, ИЛИ
         (б) match_score(плановая работа) < 0.35, но match_score(другая работа) > 0.6, ИЛИ
         (в) активность в зоне, где по графику на эту дату работ нет
SEVERITY: medium; high если (в) и длится ≥ 3 суток
```

### Р4. Тишина — `R4_silence`
```
УСЛОВИЕ: работа активна по графику
         И mh_present = 0 по всем классам ≥ 2 рабочих суток подряд
         И coverage ≥ 0.8   (иначе это Р0, а не Р4)
SEVERITY: high
```

### Р0. Низкое доверие — `R0_low_confidence`
```
УСЛОВИЕ: coverage < 0.6 ИЛИ средний quality.score < 0.5
ДЕЙСТВИЕ: отклонения по зоне НЕ формируются; в интерфейсе — серый статус
          «нет данных: ночь / осадки / камера недоступна»
```

Р0 — обязателен. Он показывает эксперту, что мы понимаем цену ложной
тревоги в системе, на которую опирается управленческое решение.

## Шаг 4. Прогноз срыва срока

```
mh_plan_total(w)   = Σ_c planned_mh[c]
mh_fact_total(w,t) = Σ_c mh_active накопленным итогом
rate(w,t)          = скользящее среднее mh_fact за 7 суток, ч/сут
forecast_finish    = t + (mh_plan_total - mh_fact_total) / rate
delay_days         = forecast_finish - finish_plan
SPI                = mh_fact_total(t) / mh_plan_to_date(t)
```

Светофор: `зелёный` SPI ≥ 0.95, `жёлтый` 0.80–0.95, `красный` < 0.80.

### Обратная задача (главная фича для руководителя)

Не «вы отстаёте на 7 дней», а **«чтобы уложиться в срок, нужен темп
46 маш.-ч/сут — это +1 экскаватор и +2 самосвала, начиная с 24.09»**:

```
required_rate = (mh_plan_total - mh_fact_total) / (finish_plan - t)
gap_mh        = required_rate - rate_current
доп_единиц[c] = ceil(gap_mh × доля_класса[c] / средняя_выработка_на_единицу[c])
```

Это превращает систему мониторинга в систему поддержки решений.
На питче показывать именно этот экран.

---

## Шаг 5. Как система признаёт ошибку

В карточке отклонения — кнопка «Не согласен», три причины:
`техника вне кадра` / `неверная норма в графике` / `ошибка распознавания`.
Обратная связь пишется в `data/feedback.jsonl` и используется для
докалибровки порогов. Показать этот цикл на питче — сильный ход:
он отвечает на вопрос эксперта «а если ваша модель ошибётся?».
